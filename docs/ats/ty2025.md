### A2A readiness sequence, independent of Form 1040 calculation work

This lane can advance in parallel with the return builder. Each item needs its
own evidence before a test transmission is attempted. No credential or secret
needs to be copied into this repo.

1. Obtain the current IRS ATS A2A service package, including the transmitter
   service WSDL and imported XSDs, MeF header schema, service endpoint, and IRS
   trust certificates. The
   [IRS MeF user-guides page](https://www.irs.gov/e-file-providers/modernized-e-file-mef-user-guides-and-publications)
   says transmitters can request the A2A SDK Toolkit by emailing
   `mefmailbox@irs.gov` with `A2A Toolkit` in the subject. Ask the IRS contact
   which current transmitter WSDL, imported schemas, ATS endpoint, and trust
   package apply to our enrolled account, and record the release and target
   environment before implementation. Publication 5830 describes the protocol
   but is not a substitute for validating against that service package. These
   A2A schemas are not present in the locally cached TY2025 return-schema bundle.
2. Confirm the issued ATS public certificate matches the production-held private
   key, that Automated Enrollment has bound it to the test system, and that the
   resulting ASID/AppSysID and ETIN are authorized for the intended ATS service.
   Record only identifiers and verification results in the deployment record,
   not private-key material here.
3. Build and locally validate the complete SOAP request against the obtained
   service package: WS-Addressing, MeFHeader, signed initial strong
   authentication, session handling, and the documented MIME/MTOM attachment
   binding. A Send request must use a valid session established by an initial
   authenticated request. Publication 5830 says subsequent requests carry the
   returned signed SAML assertion unchanged. Do not assume the existing
   `SendSubmissionsRequest` XML body or outer ZIP is a valid complete message.
4. Implement response processing and durable correlation by MessageID,
   SubmissionId, and receipt/deposit identifiers. Preserve SOAP faults and
   submission receipts; retrieve acknowledgments through the documented
   transmitter service and preserve their signed payloads and final statuses. An
   HTTP success or Send response alone is not an IRS acceptance.
5. Only after the return calculation, TY2025 return-XSD, filled-PDF, and IRS
   business-rule gates pass, transmit one authorized ATS scenario. Reconcile its
   submitted archive, receipt, and accepted acknowledgment, then record the
   scenario and exact IRS response as the acceptance evidence.

Until the current service package and registration evidence are available, the
safe engineering output is this checklist and offline archive construction, not
an inferred SOAP client or a claim of ATS readiness.

### Offline A2A evidence journal (locally tested)

`forms/f1040/2025/mef/submissions/a2a-evidence.ts` now provides a local append-only evidence
journal. It stores the exact `SendSubmissionsRequest` body and outer ZIP under a
caller-assigned MessageID, checks that its listed Submission IDs match the ZIP
entries, and archives opaque inbound response, SOAP-fault, or acknowledgment
payload bytes with SHA-256 hashes. Each inbound item must supply a previously
stored Send MessageID. Its request-body check now requires the
`SendSubmissionsRequest` service namespace, `SubmissionDataList` hierarchy, and
documented `SubmissionData` fields, so a nested or misplaced Submission ID
cannot stand in for the request structure. The electronic postmark is optional
under [Publication 5830](https://www.irs.gov/pub/irs-pdf/p5830.pdf).
Each inbound item accepts
only Submission IDs from that Send. A Send response or
fault must also supply a matching `RelatesTo` MessageID. These inbound IDs are
caller-asserted metadata; the journal cannot verify that they appear in, or are
signed with, the opaque response payload. Records are staged, file-synced, and
renamed into private local directories; reads recheck payload hashes. The caller
must supply a private storage root with permissions suitable for taxpayer PII;
restrictive new child directories and files do not make an existing parent root private. This
module does not create a CLI command, send a request, or fetch an
acknowledgment. On 2026-10-04, the current `a75f0bca` code passed **44/44**
focused submission-archive and evidence-journal tests with
`deno test --allow-read --allow-write --allow-net=www.irs.gov
forms/f1040/2025/mef/submissions/submission-archive.test.ts
forms/f1040/2025/mef/submissions/a2a-evidence.test.ts`. The first local attempt omitted
the IRS PDF-template network permission and produced one `NotCapable` failure;
the rerun with the repository's documented network scope passed. This verifies
local archive and journal behavior only; no IRS response was parsed or received.

The journal deliberately does **not** parse or validate a signed SOAP message,
verify IRS signatures, assign an IRS receipt/deposit identifier, infer a final
status, or mark a return accepted. `acknowledgment_payload` is only an opaque
payload classification supplied by a future validated transport/parser. Full
response processing remains blocked on the current IRS ATS transmitter WSDL,
imported service and MeFHeader schemas, endpoint/trust package, enrolled ASID
and ETIN, and the signed authentication/session/MTOM rules. Only after that
protocol package is validated can a parser authenticate response `MessageID`,
`RelatesTo`, receipt/deposit IDs, acknowledgment Submission IDs, and final
acceptance status before passing those observed identifiers to the journal.
